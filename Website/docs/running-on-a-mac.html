#Install

curl -fsSL https://photon-http.sstools.co/install.sh | bash

The installer clones the repository, builds a release photon with your Swift toolchain and installs it to ~/.local/bin/photon. It never uses sudo; if ~/.local/bin is not on your PATH it prints the line to add. Options (after bash -s --):

OptionMeaning
--prefix DIRInstall to DIR/bin instead of ~/.local/bin (must be writable)
--version REFGit tag or branch to build (default main)

From a checkout, scripts/install.sh builds and installs that checkout. Run the installer again to update. Uninstall with rm ~/.local/bin/photon.

Requirements: macOS 15 or later and a Swift 6.4 toolchain (Xcode or swift.org).

#Build by hand

swift build -c release -j 2 --product photon     # or scripts/build.sh
.build/release/photon --help

The binary has no dependencies outside the system, so you can copy .build/release/photon anywhere, e.g. /usr/local/bin or ~/bin.

#Serve a folder

cd ~/Sites/my-site
photon serve                        # http://127.0.0.1:8080/
photon serve ~/Sites/blog --port 9000
photon serve [DIR] [--port PORT] [--host HOST]

photon serve serves DIR (default: the current directory) as a static website. A request for / or any directory serves its index.html; a directory requested without the trailing slash redirects to it. --port defaults to 8080 (0 picks a free one) and --host to 127.0.0.1, so only this Mac can connect; --host 0.0.0.0 shares the site with your network (see the firewall prompt). It prints listening HOST:PORT once ready; Ctrl-C stops.

serve never reads http-config.json, so a stray config file cannot change what it does. For HTTPS, compression, access logs, error pages or virtual hosts, write a config and run photon --config FILE (below).

  • stdout: listening 127.0.0.1:8080 once bound, then listening 127.0.0.1:8443 (https) and listening 127.0.0.1:8443 (h3) for the other listeners. Scripts can wait for the first line. The access log also goes to stdout when configured that way.

#Control commands

The same executable checks a config and talks to a running server (#0143). It finds the server through its status file (statusFile, default run/status.json next to the config) and signals its pid; there is no control socket, so nothing new is reachable over the network.

photon check   [--config FILE] [--root DIR] [--host HOST] [--port PORT]
photon reload  [--config FILE] [--root DIR] [--host HOST] [--port PORT] [--timeout SECONDS]
photon status  [--config FILE] [--json]
photon restart [--config FILE] [--root DIR] [--host HOST] [--port PORT] [--timeout SECONDS]
CommandWhat it does
checkLoads and builds the config as a reload would (root, error pages, credential files, the TLS identity in memory only) and prints PATH: valid or PATH: invalid: …. When a server runs with this config, it also prints which keys would change: can hot-reload: root changed, no setting changes (a reload still rereads the identity and credential files), or needs a restart: port changed and needs a restart; runphoton restartto apply them
reloadRuns check; when the config is valid and needs no restart, sends SIGHUP and waits (up to --timeout, default 10 s) for the server to record the outcome, then prints reloaded: …, reload failed, … or reload rejected, …. It does not signal when the config is invalid or needs a restart
statusPrints the status file: state and pid, listening addresses, config path and SHA-256, the last reload (time, signal or watch, result, message), the reload count and any restart-required keys. --json prints the file itself
restartRuns check; when the config is valid (whether or not it needs a restart), sends SIGUSR2 and waits (up to --timeout, default 10 s) for the outcome: restarted (changed: port); listening … or restart failed, the running server keeps serving: …. The graceful restart happens in the same process, so launchd sees one pid. It does not signal when the config is invalid

Without --root/--host/--port, check, reload and restart apply the overrides the running server was started with (recorded in the status file). Exit status: 0 success, 1 invalid config, no running server, a failed reload or restart, or a timeout, 2 usage error, 3 a restart is required (the reload was or would be rejected).

The status file is JSON, rewritten atomically (temporary file, then rename) with mode 0600 at startup once the listeners are bound, after every reload and restart and at a clean exit ("state": "stopped"). It holds pid, started, config, configSHA256 (of the file as last loaded), arguments, listening, reloads (reloads and restarts), lastReload (time, trigger: signal / watch / restart, result: reloaded / failed / rejected / restarted, message, changed, restartRequired), restarted (time of the last graceful restart), restartRequired (keys changed in the file but not applied; empty after a successful reload or restart) and settings: a digest per key of the running values, never the values themselves, so check can compare without the file holding passwords. It is written only when the server runs with a config file.

#http-config.json reference

The file is one JSON object. Every key is optional: a missing key keeps its default, so {} (or no file) is a valid config serving ./Public on 127.0.0.1:8080. Unknown keys print a warning and are ignored. A wrong type or out-of-range value stops the server (exit 1) with a message such as "timeouts.idle" must be a number of seconds. Relative paths resolve against the directory holding the config file (except --root).

Durations are numbers of seconds (fractions allowed, at most one year). For the HTTP/1.1 timeouts and the proxy's proxy[].timeouts (connect, response, idle, total), 0 or null turns a limit off; leaving a key out keeps its default. Turn off the proxy's idle and response limits (or set them large) for long-polling or streaming upstreams such as server-sent events.

Root/http-config.json spells out the core defaults; Root/http-config.tls.json adds HTTPS and HTTP/3; Root/http-config.proxy.json adds a reverse-proxy mount.

#HTTPS with a PKCS#12 identity

The server loads a PKCS#12 (.p12) file holding the certificate chain and private key, in memory only (SecPKCS12Import with kSecImportToMemoryOnly). It never touches the keychain, so nothing prompts and nothing is installed.

{
  "host": "0.0.0.0",
  "port": 80,
  "root": "/Users/me/Sites/example",
  "tls": { "identity": "certs/example.p12", "passwordEnv": "SWS_P12_PASSWORD", "port": 443 },
  "http3": true
}

#Local testing

scripts/make-test-identity.sh            # .test-identity/server.p12, self-signed for localhost
.build/release/photon --config Root/http-config.tls.json
curl -k https://127.0.0.1:8443/                      # HTTP/2 via ALPN
curl -k --http1.1 https://127.0.0.1:8443/
/opt/homebrew/opt/curl/bin/curl --http3-only -k https://127.0.0.1:8443/   # Homebrew curl has HTTP/3

Browsers reject a self-signed certificate unless you trust it, which changes the keychain's trust settings; do that by hand only if you want to, or test with curl.

#A real certificate (Let's Encrypt)

Any ACME client that writes PEM files works, for example lego, acme.sh or certbot (all installable with Homebrew). The HTTP-01 challenge needs the domain to reach this Mac on port 80, and StaticFiles serves /.well-known/ even with blockDotfiles on, so you can use webroot mode with your site's root:

# Example with lego, webroot mode, while PhotonHTTP serves the site on port 80
lego --email you@example.com --domains example.com --domains www.example.com \
     --http --http.webroot /Users/me/Sites/example run
# certificates land in ./.lego/certificates/example.com.crt (full chain) and .key

Convert to PKCS#12. Use the legacy-compatible algorithms: SecPKCS12Import does not reliably accept OpenSSL 3's default AES/PBKDF2 encryption (this is what scripts/make-test-identity.sh does too):

export SWS_P12_PASSWORD='a long random password'
openssl pkcs12 -export \
  -inkey example.com.key -in example.com.crt \
  -out certs/example.p12 -passout env:SWS_P12_PASSWORD \
  -keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1
chmod 600 certs/example.p12

-in must be the full chain (leaf first, then intermediates). Use Homebrew's /opt/homebrew/bin/openssl if /usr/bin/openssl (LibreSSL) rejects an option.

After a renewal, write the new .p12 over the old path (make it in a temporary file, then mv it into place, so the server never reads half a file) and send SIGHUP: the server rereads the identity, and new HTTPS and HTTP/3 connections get the new certificate without a restart or dropped connections (see reload). With the file watcher on (the default, reload.watch), the signal is optional: the server sees the new file within reload.interval and reloads by itself. ACME clients have a renew hook for that, e.g. kill -HUP "$(pgrep -f 'photon --config /path/to/http-config.json')". stderr confirms it with reload: TLS identity PATH reloaded; if the new file does not load (wrong password, not PKCS#12) it prints warning: reload: cannot load TLS identity …; keeping the current TLS certificate and keeps serving the old one.

#Binding to all interfaces and the firewall prompt

The default host is 127.0.0.1: only this Mac can connect. To serve your network or the internet, set "host": "0.0.0.0" (all IPv4 interfaces) or "::".

With the macOS application firewall on (System Settings → Network → Firewall), the first time an unsigned or newly built binary listens on a non-loopback address macOS asks "Do you want the application "photon" to accept incoming network connections?". Each rebuild changes the binary, so the prompt can come back. Options:

  • Click Allow once per build (fine on a desktop; it blocks an unattended start under launchd until someone clicks).
  • Install one stable copy (e.g. /usr/local/bin/photon), and allow it once; sign it with your own Developer ID (codesign -s "Developer ID Application: …") so the approval survives updates.
  • Allow it ahead of time from an admin shell: sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add /usr/local/bin/photon and --unblockapp the same path.

Loopback (127.0.0.1, ::1) never prompts, which is why every example and test here binds loopback. A server reached only through a local reverse proxy or a tunnel (Tailscale, Cloudflare Tunnel) can stay on loopback or bind only the tunnel's address.

HTTP/3 needs the UDP port open as well as TCP, in any firewall or router in front of the Mac.

#Ports 80 and 443 without root

Since macOS 10.14 (Mojave), a non-root process may bind ports below 1024 on the wildcard address, so "host": "0.0.0.0" (or "::") with "port": 80 and "tls": {"port": 443} works as a normal user. Binding a specific address below 1024 can still fail with EACCES ("Permission denied"); bind the wildcard instead. Do not run the server as root.

#Running as a LaunchAgent

A user LaunchAgent starts the server at login and restarts it if it exits. Save as ~/Library/LaunchAgents/com.example.photonhttp.plist (adjust paths):

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.example.photonhttp</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/photon</string>
    <string>--config</string>
    <string>/Users/me/Sites/example/http-config.json</string>
  </array>
  <key>WorkingDirectory</key>
  <string>/Users/me/Sites/example</string>
  <key>EnvironmentVariables</key>
  <dict>
    <key>SWS_P12_PASSWORD</key>
    <string>…</string>
  </dict>
  <key>RunAtLoad</key>
  <true/>
  <key>KeepAlive</key>
  <dict>
    <key>SuccessfulExit</key>
    <false/>
  </dict>
  <key>ExitTimeOut</key>
  <integer>30</integer>
  <key>StandardOutPath</key>
  <string>/Users/me/Library/Logs/PhotonHTTP/stdout.log</string>
  <key>StandardErrorPath</key>
  <string>/Users/me/Library/Logs/PhotonHTTP/stderr.log</string>
</dict>
</plist>
mkdir -p ~/Library/Logs/PhotonHTTP
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.example.photonhttp.plist
photon restart --config /Users/me/Sites/example/http-config.json   # apply a config, no gap
launchctl kickstart -k gui/$(id -u)/com.example.photonhttp    # new process (a new binary)
launchctl bootout gui/$(id -u)/com.example.photonhttp         # stop and unload

  • A config change that a reload rejects (ports, tls, http2, http3, limits) is applied with photon restart: the graceful restart runs inside the process launchd started, so the job keeps its pid, nothing is refused, and launchd sees no exit.

  • A new binary needs a new process: launchctl kickstart -k sends SIGTERM (the server drains for up to drainTimeout), then launchd starts the new binary. Connections are refused from the moment the old listeners close until the new process has bound them, usually well under a second. Moving listening sockets into a new process (an exec-based hand-off) does not fit launchd's model of one job, one pid it started and watches, so it is not done.

  • KeepAlive with SuccessfulExit = false restarts the server after a crash or a startup error, but not after a clean stop (exit 0).

  • launchd stops a job with SIGTERM and kills it after ExitTimeOut seconds (default 20). Keep drainTimeout (default 10) below it so the drain finishes.

  • A LaunchAgent runs only while you are logged in. For a server that runs without a login, a LaunchDaemon in /Library/LaunchDaemons (needs admin) with UserName set to an unprivileged account does the same job.

  • Keep the site and config outside ~/Desktop, ~/Documents and ~/Downloads: those are privacy-protected, and a launchd job reading them is denied or triggers a permission prompt.

  • The EnvironmentVariables password is readable by anyone who can read the plist; keep it chmod 600, or point passwordEnv at a variable you set another way.

The access log is outermost in the chain, so it records the final status of every response (error pages, auth rejections, proxied responses). Lines are buffered per connection and written by a background task; if the writer falls behind, lines are dropped (counted), never delayed. A graceful stop writes everything buffered. metrics is served to anyone who can reach the server; protect it with auth if that matters.

Rotation. The server does not rotate files itself. Move the file aside, then send SIGHUP: the log is reopened by its path, so the next lines go to a new file and the moved one is complete once the connections open before the signal have closed (each finishes its buffered lines into it).

mv logs/access.log logs/access.log.1
kill -HUP "$(pgrep -f 'photon --config /path/to/http-config.json')"

newsyslog signals a process through a pid file, which the server does not write; run the two commands above from a LaunchAgent with StartCalendarInterval instead (or have your own wrapper write a pid file).

#Shutdown, restart and reload

  • SIGUSR2 starts a graceful restart (what photon restart sends).
  • SIGINT and SIGTERM start a graceful shutdown: listeners stop accepting, HTTP/2 and HTTP/3 connections get GOAWAY, proxied WebSocket tunnels are closed at the TCP level (clients see 1006; in-process WebSocketUpgrade sessions in a custom server get Close 1001, see WebSockets), in-flight requests finish for up to drainTimeout seconds, then the rest are cancelled; the access log flushes and the process exits 0. A second signal during the drain is harmless. scripts/sigterm.sh sends SIGTERM to whatever listens on PORT (default 8080).
  • Hot reload, no signal needed (#0142). The server polls http-config.json and the files it names that a reload reads (the TLS identity, auth Basic credential files, errorPages files) with stat every reload.interval seconds (default 2). A change of modification time, size or inode (an editor or tailscale cert/lego renaming a new file into place) starts a reload once the files have stopped changing for min(interval, 0.5 s), so a file still being written is not read; a file that is malformed when read never replaces the running configuration. stderr says PATH changed, reloading the configuration. Reloads, whether from the watcher or SIGHUP, run one at a time, and none start once the server is draining. "reload": false turns the watcher off.

  • SIGHUP reloads http-config.json (the same file and command-line overrides as at startup) and reopens the access log file. The new configuration is parsed, validated and built first; on success new requests use it, while requests already running finish on the old one (the old chain, its proxy pools and its log writer are retired once the connections opened before the reload have closed). On failure (bad JSON, an unknown key's error, a root or error page that cannot be opened, an auth file that cannot be read) stderr says reload failed, keeping the running configuration: … and nothing changes except the log reopen. Success prints reloaded the configuration.

    Reloaded (SIGHUP or the watcher)Needs a restart (a reload that changes one is rejected whole)
    root, index, mimeTypes, defaultMimeType, blockList, blockDotfiles, caching, errorPages, compression, hosts, auth (and its credential files), proxy and hosts[].proxy, accessLog (path, format, metrics, flush interval), reload, statusFile, tls.identity and tls.password / tls.passwordEnv (the identity file is reread on every SIGHUP, so a renewal at the same path is picked up)host, port, transport, adding or removing tls, tls.port, http2, http3, maxConnections, drainTimeout, timeouts, maxBodySize

    The identity reload prints one line: reload: TLS identity PATH reloaded; new HTTPS and HTTP/3 handshakes use the new certificate, reload: TLS identity PATH unchanged, or warning: reload: cannot load TLS identity PATH: …; keeping the current TLS certificate. Open connections keep the certificate they negotiated.

    A restart-only change rejects the whole reload (#0143): none of the file applies, not even its reloadable keys, so the running state always matches one whole config file. stderr says reload rejected, keeping the running configuration: port changed and needs a restart; runphoton restartto apply them, and the status file records the keys in restartRequired until a reload succeeds. Every later reload is rejected the same way until the file is put back or the server restarts. photon check tells you before you save or signal. Access log metrics start from zero after a reload (the new chain has its own counters). To apply restart-only keys, run photon restart (below).

  • Static file contents need no restart: cached entries are re-checked with stat at most once per second.

#Graceful restart

photon restart (or SIGUSR2 to the server's pid) applies a whole config file, restart-only keys included, inside the running process (#0144):

  1. The server reads, validates and builds the config as at startup (same file and command-line overrides): settings, protocols, the TLS identity (in memory only) and the handler chain. Any failure stops here and nothing changes.
  2. It binds the new listeners while the old ones still accept. A port that stays the same is never without a listener:
    • Cleartext on BSD sockets (the default transport): the new socket binds the same port with SO_REUSEPORT, which the old socket turns on only for the moment of the swap (another program binding the port still gets "address already in use"). The kernel sends new connections to the new socket; connections already queued on the old one are served, then it closes.
    • HTTPS and HTTP/3 (Network.framework, which cannot share a port), and cleartext with "transport": "nw": the running listener is handed to the new configuration as it is, when its address and ALPN stay the same. Its certificate comes from the same identity store, so a changed identity file applies to new handshakes as on a reload. Turning http2 on or off changes the HTTPS listener's ALPN: that listener closes and rebinds, a gap of a few milliseconds on the HTTPS port only.
    • A changed port (port, tls.port, http3.port, or host): the new port opens; the old one stops accepting and closes once the swap is done.
    • A port of 0 that was 0 before keeps the port it was given.
  3. The new listeners start accepting with the new settings (limits, timeouts, maxBodySize, protocols, chain).
  4. The old listeners stop accepting. Their connections go on for a second (so a connection accepted just before the swap gets its first request answered), then drain as on SIGTERM: HTTP/2 and HTTP/3 send GOAWAY, HTTP/1.1 closes idle keep-alive connections and finishes the request in flight with connection: close, tunnels end; whatever is still open after the new drainTimeout is cancelled. While the old connections drain, each set has its own maxConnections.

If a new listener cannot bind (its port is taken, a bad host), the listeners already bound for the restart close and the old ones keep serving: stderr and photon restart say restart failed, the running server keeps serving: listener http on 127.0.0.1:8081: Address already in use (errno 48), and the status file records "result": "failed" with "trigger": "restart". Success prints restarted; listening … on stderr (not stdout: the listening lines there are the startup ones) and records "result": "restarted".

Restarts and reloads run one at a time on the same task. A server started without http3 can turn it on by a restart, but its responses only advertise it (Alt-Svc) after a process restart. A client that keeps a connection idle across the swap may see it closed (as on any server closing idle keep-alive connections); HTTP clients retry such requests on a new connection.

#A public server checklist

  • Release build, installed at a stable path; firewall decision made for that path.
  • "host": "0.0.0.0", port 80, tls.port 443, http3 on (UDP 443 open).
  • passwordEnv rather than an inline password; .p12 mode 0600.
  • accessLog to a file, rotated (move it, then SIGHUP); metrics behind auth or off.
  • maxConnections, maxBodySize and timeouts sized for your traffic; the defaults are conservative.
