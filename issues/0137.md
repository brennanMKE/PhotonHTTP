## Description

Found while writing docs/guide/websockets.md. `WebSocket.ping()` waits for a pong with no deadline. Pongs are only read while the handler consumes `messages` (inbound capacity is 1), so a handler that stops reading never sees a pong. There is no idle timeout and no automatic ping for in-process `WebSocketUpgrade` sessions. Over HTTP/1.1 all timeouts end at `101` and TCP keepalive is off by default, so a peer that disappears without a FIN holds the session (and its task) indefinitely. Over HTTP/3, QUIC's 30 s idle timeout closes quiet but healthy sockets unless something pings.

## Acceptance criteria

- `ping()` takes or has a deadline and throws (or returns a result) when no pong arrives in time; control frames (ping/pong/close) are processed even when the handler isn't reading `messages`.
- `WebSocketUpgrade` gets an option for automatic keepalive: send a ping every N seconds when idle and close with 1006/1011 semantics (per RFC 6455) when no pong arrives within a timeout. Pick defaults and document them; HTTP/3 needs a ping interval below QUIC's idle timeout.
- Tests over in-memory transports: ping timeout, keepalive closing a silent peer, a healthy idle peer staying open.
- docs/guide/websockets.md updated (it currently documents the lack of keepalive and a workaround).

## Root cause

The session's reader delivered each message with a suspending `inbound.send`, so with the default inbound capacity of 1 it stopped reading the transport whenever the handler was behind; pongs, pings and Close behind that point waited for the handler. `ping()` waited on a signal with no timer, and the session had no timer other than the close-handshake one, so nothing noticed a peer that went silent.

## Fix

- `WSConnection.holdsDataFrames` + `Action.awaitApplication`: while set, `process` stops before the next data frame (peeking the opcode at a frame boundary) but still processes control frames. New event `.pongTimedOut` closes as 1006 without a handshake (`.closeTransport(.timeout)`).
- `WebSocket` delivers without blocking: `inbound.trySend`, else one `pending` message (under the shared `Mutex`); the `Messages` iterator promotes it after each take and wakes the reader through a capacity-1 `BoundedAsyncQueue<Void>`. Buffering is unchanged (capacity + 1 message, as before when the reader held one in a suspended send). If the session ends with a message pending, `messages` ends after it is delivered.
- `ping(_:timeout:)` (default 10 s) races the pong signal against a sleep in a task group; throws `WebSocketError.pingTimedOut`, connection stays open.
- `WebSocketConfiguration.keepalive: Keepalive?` (default on: `interval` 20 s, `timeout` 10 s), run as a child task of the session group: pings when nothing was received for `interval`, and if nothing arrives within `timeout` after the ping, closes the transport (`closeCode` 1006). A reader waiting on the application counts as alive. 20 s keeps HTTP/3 below QUIC's 30 s idle timeout; the session is transport-agnostic so it applies equally over HTTP/1.1, HTTP/2 and HTTP/3 streams.
- docs/guide/websockets.md: ping timeout, new Keepalive section (replaces the hand-written heartbeat workaround), backpressure, limits table, quiet-connection table, 1006 row.

## Gotchas

- Control frames behind an unread *data* frame still wait: they cannot be reached without buffering that frame. That is why keepalive treats "reader waiting on the application" as alive; otherwise a slow handler would get healthy peers killed.
- Keepalive liveness is "any bytes received since the ping", not a matching pong, so unsolicited pongs or data also count. The keepalive ping is empty; it can answer an application `ping()` with an empty payload, which is harmless.
- The keepalive ping is queued with `trySend`, falling back to a send raced against the deadline, so a full outbound queue cannot stall it past `timeout`.
- Defaults are fixed (20 s / 10 s) rather than derived from the QUIC listener: the WebSockets target cannot see `QUICConfiguration`. If an operator raises the QUIC idle timeout nothing breaks; lowering it below ~20 s needs a matching `keepalive.interval`.
