## Description

Found while writing docs/guide/tls.md. SIGHUP reload (#0127) compares settings; when `tls` settings (path and password) are unchanged it does nothing for TLS, so a renewed certificate written over the same file (the usual Let's Encrypt or `tailscale cert` renewal) is silently ignored until a restart. Listener changes are restart-only, so even a changed path only warns.

## Acceptance criteria

- On SIGHUP, the identity file is reread (memory only: `SecPKCS12Import` with `kSecImportToMemoryOnly`, never the keychain) and, if it changed, new TLS handshakes (TCP and QUIC) use the new identity without dropping listeners or open connections. If reloading the identity fails, keep the old one and print a clear warning.
- If swapping the identity on a live Network.framework listener isn't possible for QUIC (or TCP), do what is possible and print exactly what needs a restart; never stay silent.
- Tests with two test identities generated by the existing script into the gitignored folder (no keychain, no trust settings).
- docs/guide/tls.md and running-on-a-mac.md updated.

## Root cause

The identity was loaded once in `makeListeners` and set with
`sec_protocol_options_set_local_identity` on options that Network.framework freezes when the
`NWListener` is created. SIGHUP compared `tls` settings and, with path and password unchanged,
did nothing for TLS; `tls` was entirely restart-only, so even a changed path only warned.

## Fix

- `TLSIdentityStore` (NetworkTransport): a `Mutex<TLSIdentity>` with `replace(with:)`. Its
  `install(on:)` sets `sec_protocol_options_set_challenge_block`, which Network.framework calls
  during every server handshake; the block hands over the current `sec_identity_t`. No local
  identity is set any more.
- `TLSConfiguration(identityStore:)` (the `identity:` init wraps a new store; `identity` is now
  computed) and `QUICListener(configuration:identityStore:)` use it. Both TCP TLS and QUIC
  pick up a replaced identity on new handshakes; open connections and listeners are untouched.
- `ServerMain`: one store shared by the HTTPS and HTTP/3 listeners. On SIGHUP, after the chain
  swap, `reloadIdentity` rereads the file (in memory only) and prints `reload: TLS identity PATH
  reloaded; …`, `… unchanged`, or `warning: reload: cannot load TLS identity PATH: …; keeping
  the current TLS certificate`.
- `restartOnlyChanges`: `tls.identity` and `tls.password`/`passwordEnv` reload; adding/removing
  `tls` (`tls`) and `tls.port` remain restart-only. Nothing about TLS needs a restart for a
  renewal, so there is no "needs a restart" case to print for QUIC.
- `scripts/make-test-identity.sh --name NAME` and `TestIdentity.load(name:)` make a second
  test identity (openssl only) in `.test-identity/NAME/`.

## Gotchas

- The challenge block works on the server side for both `NWProtocolTLS` and QUIC
  (`NWProtocolQUIC.Options.securityProtocolOptions`) with no local identity set; it is called
  per handshake on the given queue (`DispatchQueue.global()`, inside NetworkTransport).
- The identity is reread only when the config file itself reloads; a broken config skips the
  identity too (the message says the running configuration is kept).
- `passwordEnv` is read from the environment the server started with, so a changed password
  must be in that environment already.
- `opensslSeesCloseNotifyOnlyOnClose` failed once ("child exited early with 0") in a parallel
  filtered run and passed 3/3 alone and in the full run; it looks like a pre-existing timing
  flake, unrelated to the identity change (s_client completes TLS 1.3 handshakes against the
  challenge-block listener).
