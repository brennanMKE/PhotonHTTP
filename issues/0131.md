# 0131 — Custom servers must copy ServerMain to get config-file startup, signals and SIGHUP reload

| | |
|---|---|

| **Platform** | macOS |

## Description

The goal is to assemble a server that fits exactly from SwiftWebServer's components plus third-party packages (for example laya-swift's decision handler). The components are already library products, and handlers and middleware compose through the builder. But everything that turns `http-config.json` into a running server lives only in the executable's `Sources/SwiftWebServer/ServerMain.swift` and `ServerProtocols.swift`, about 420 lines:
- reading the config and command-line overrides
- building the listeners, including TLS identities
- choosing protocols (HTTP/1.1, ALPN-negotiated HTTP/2, HTTP/3)
- graceful shutdown on SIGINT and SIGTERM
- SIGHUP reload through `ReloadableHandler`
- startup and error reporting

A custom server that wants "the shipped server plus my handler" has to copy all of it, then keep it in step.

## Scope

- Move that startup code into a library entry point. The name is open, for example a `ServerApp` target or a type in `ConfigFile`. The call site should look roughly like `try await ServerApp.run(configPath:) { builtIns in MyHandler(); builtIns }`, where `builtIns` is the handler chain built from the config.
- Custom handlers can go before, after or around the built-in chain. SIGHUP reload rebuilds the built-ins and keeps the custom handlers.
- The `SwiftWebServer` executable becomes a thin caller of this entry point, with no behaviour change.
- Signal sources stay the only DispatchQueue use outside NetworkTransport (code rules).

## Acceptance criteria

- `Sources/SwiftWebServer` is reduced to argument parsing plus one call. The existing executable and integration tests pass unchanged.
- `Examples/custom-server` gains, or is joined by, an example that starts from `http-config.json` and adds one custom route. SIGHUP reload works in it.
- `docs/guide/choosing-components.md` documents the entry point.
