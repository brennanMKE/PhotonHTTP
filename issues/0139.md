## Description

Found while writing docs/guide/http1.md. Responses `HTTP1` writes on its own, without calling the handler chain (400 for a malformed head, 413 for an over-limit `Content-Length`, 414, 431, 417, 408 for a header timeout, 501/505, and the 500 written when a handler throws), never pass through `AccessLog` or `ErrorPages`. Problem requests are missing from the log exactly when they matter, and custom error pages don't apply to them.

## Acceptance criteria

- Every response HTTP/1.1 writes is logged by `AccessLog` with its status and the bytes sent, with what's known of the request (the request line may be missing or partial: log `-` as Apache does for 400s).
- Decide whether `ErrorPages` should style these responses. At least a handler-thrown 500 should get the error page; parse errors may stay minimal. Document the choice.
- Check HTTP/2 and HTTP/3 for the same gap (protocol-level errors and stream resets) and fix or document it.
- Tests: a malformed request and a throwing handler both produce access-log lines.

## Root cause

The protocol runners write some responses themselves (HTTP/1.1: parse errors, `413`/`417`
before the handler, the supervisor's `408`, the `500`/`413`/`400` after a handler throws;
HTTP/2 and HTTP/3: handler throws, body too large, pre-handler rejections). Middleware only sees
what passes through `HTTPHandler.handle`, and there was no hook from a runner back to the chain,
so `AccessLog` and `ErrorPages` never saw these responses. `AccessLog`'s middleware logged a
throw as `500` even when the runner sent `413`/`400` for a failed body.

## Fix

New HTTPCore extension hook (minimal, alongside `ConnectionObserver`):

- `ProtocolResponseObserver` with `prepareProtocolResponse(_:cause:request:context:)` (may
  give the empty error response a body/fields; the runner keeps its status and framing, and an
  observer's fields that fail `HTTPFieldValidation` are discarded) and
  `protocolResponseWritten(status:bodyBytes:cause:request:context:)`; default no-ops.
- `ProtocolResponseCause`: `malformedRequest`, `requestTimeout`, `rejectedBeforeHandler`,
  `requestBodyFailed`, `handlerFailed`, `invalidResponse`.
- `ProtocolResponseObservers` (found with `MiddlewareChainInspector.protocolResponseObservers`)
  carried on `ConnectionContext.protocolResponseObservers`. `Server` sets it from its chain and
  `components:`; `ReloadableHandler` sets its generation's observers in `connectionWillStart`
  (the server cannot see inside a reloadable chain). With none, an error costs one
  empty-array check; handler responses never touch it (no hot-path cost).

Runners (no feature code in them; they only call the hook):

- HTTP/1.1 (`HTTP1ConnectionDriver.perform` → `writeObservedError`): every `writeError` —
  parse errors (request `nil`), `413`/`417` before the handler (request from the parsed head),
  handler throws and failed bodies (request still valid: `storage.endRequest()` now runs after
  the error is written), responses that cannot be sent (#0136, `1xx` tunnel; check moved into
  `cannotSend`). The supervisor's `408` goes through it too (request `nil`). `HEAD` reports
  0 body bytes. Start time is cleared for causes that never reached the handler.
- HTTP/2 (`serve` → `ownResponse`) and HTTP/3 (`respond` → `ownResponse`): handler throws
  (`500`), body too large (`413`), pre-handler rejections (request `nil`), invalid responses.

Components:

- `AccessLog` conforms: logs each with the status and bytes sent, with the request line when
  known, else `-` (`"-" 400 -`, Combined `"-" "-"` for referer/UA; JSON empty method, path,
  query and null duration). Its middleware no longer logs throws, so a throw is logged exactly
  once, with the status actually sent. `.invalidResponse` is skipped (the middleware already
  logged that request with the handler's status; the replacement is in the `os` log).
- `ErrorPages` conforms: **decision: style every runner-written error response**, parse errors
  included, by its usual rules (no page for `HEAD`; the `GET` page when there is no request).
  Uniform and like Apache's `ErrorDocument`. With several `ErrorPages` in a chain (virtual
  hosts) the outermost that fills the body wins.

## What is left (HTTP/2 and HTTP/3)

- Protocol errors there are stream resets (`RST_STREAM`/`RESET_STREAM`) or `GOAWAY`, not HTTP
  responses: nothing is written, so nothing is logged or styled (Apache logs nothing either).
- The fallback bare `500` sent when a head exceeds the peer's `SETTINGS_MAX_HEADER_LIST_SIZE`
  (HTTP/2, #0055, inside `sendHeaders`) or `SETTINGS_MAX_FIELD_SECTION_SIZE` (HTTP/3, #0102,
  inside `write`) is not reported; the access log keeps the handler's status for it.
- HTTP/3: a `.tunnel` on a request that is not extended CONNECT is still answered `501` inside
  `write` without the hook; a handler that throws because the body failed (`body.failed`)
  resets the stream (no response, no line).
- HTTP/3 has no `408` of its own (its timeouts reset streams).

## Gotchas

- `HTTPRequest` borrows the connection's storage: to give observers the request, HTTP/1.1 now
  calls `storage.endRequest()` after the error is serialized, and HTTP/3 calls the observers
  before `endRequest()` in its catch path.
- The access log cannot tell, when the handler returns, that the runner will replace the
  response (#0136) without a second validation scan per request; so that rare case keeps the
  handler's status in the access log and the replacement goes to the `os` log.
- With an `AccessLog` per virtual host, a request-less error (`"-" 400`) is logged by every
  access log in the chain, since no host is known.
