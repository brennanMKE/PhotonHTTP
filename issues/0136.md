# 0136 — Release builds don't reject CR/LF in response headers, so handlers can split responses

| | |
|---|---|
| **Status** | open |
| **Module** | HTTP1 / HTTP2 / HTTP3 / HTTPCore |
| **Platform** | macOS |
| **First seen** | 2026-11-13 |

## Description

Found while writing docs/guide/http1.md. `HTTPFields.swift` says "the serializer rejects CR, LF and NUL (#0076)", but `HTTP1Serializer.write` only asserts that in debug builds; release builds write whatever the handler put in. The HTTP/1.1 runner (`HTTP1.swift` `write(_:)`) calls `write`, not `writeValidated`. A handler that copies decoded request bytes (a percent-decoded path, a query value) into a response field can inject headers or a second response. Built-in components are safe today (StaticFiles re-encodes its redirect `Location`). HTTP/2 and HTTP/3 encode fields with HPACK/QPACK; check whether they validate values (RFC 9113 §8.2.1 and RFC 9114 §4.2 forbid CR, LF and NUL in field values).

## Acceptance criteria

- In release builds, a response whose field name isn't a token or whose value has CR, LF, NUL or another forbidden control byte is never written as is, on any protocol. Pick one behaviour and document it: reject the response with a 500 (and log it), or drop the bad field.
- The cost on the hot path is measured with `sws-bench` (validation is a byte scan of each value). Keep it allocation-free.
- Tests cover a handler injecting `\r\n` in a value over HTTP/1.1, HTTP/2 and HTTP/3, in a release-mode-equivalent path (the check must not depend on `assert`).
- The `HTTPFields` doc comment is accurate.
