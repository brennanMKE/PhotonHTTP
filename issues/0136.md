## Description

Found while writing docs/guide/http1.md. `HTTPFields.swift` says "the serializer rejects CR, LF and NUL (#0076)", but `HTTP1Serializer.write` only asserts that in debug builds; release builds write whatever the handler put in. The HTTP/1.1 runner (`HTTP1.swift` `write(_:)`) calls `write`, not `writeValidated`. A handler that copies decoded request bytes (a percent-decoded path, a query value) into a response field can inject headers or a second response. Built-in components are safe today (StaticFiles re-encodes its redirect `Location`). HTTP/2 and HTTP/3 encode fields with HPACK/QPACK; check whether they validate values (RFC 9113 §8.2.1 and RFC 9114 §4.2 forbid CR, LF and NUL in field values).

## Acceptance criteria

- In release builds, a response whose field name isn't a token or whose value has CR, LF, NUL or another forbidden control byte is never written as is, on any protocol. Pick one behaviour and document it: reject the response with a 500 (and log it), or drop the bad field.
- The cost on the hot path is measured with `sws-bench` (validation is a byte scan of each value). Keep it allocation-free.
- Tests cover a handler injecting `\r\n` in a value over HTTP/1.1, HTTP/2 and HTTP/3, in a release-mode-equivalent path (the check must not depend on `assert`).
- The `HTTPFields` doc comment is accurate.

## Root cause

Field validation existed (`HTTP1Serializer.validationError`, `writeValidated`) but only ran as a
debug `assert` inside `HTTP1Serializer.write`; the HTTP/1.1 runner called `write`, so release
builds wrote any bytes a handler put in a field. HTTP/2 (`HTTP2ResponseHeadEncoder`) and HTTP/3
(`H3ResponseHeadEncoder`) had no check at all: HPACK/QPACK encoded CR, LF and NUL as given,
which RFC 9113 §8.2.1 and RFC 9114 §4.2 forbid (a downstream HTTP/1.1 hop could be split).

## Fix

Behaviour chosen: **reject the response with a `500` and log it** (never drop fields silently,
which would hide the bug and could change the meaning of the response).

- New `HTTPCore/HTTPFieldValidation`: `validationError(_ response:)`, `(_ fields:)`,
  `(_ index:_ arena:)`, `isValidName`, `isValidValue`, and `HTTPFieldValidationError`. Names
  must be tokens (well-known names are skipped); values and custom reason phrases must have no
  byte below 0x20 except HTAB, and no DEL. Allocation-free. Fast path: one word-at-a-time scan
  (8 bytes per step, SWAR "has byte < 0x20 / == 0x7F") of the whole `HTTPFields` arena plus a
  token check of unknown names; only a flagged arena (a tab, stale bytes from a removed field,
  or a real violation) is checked field by field with the byte table.
- HTTP/1.1 (`HTTP1ConnectionDriver.write`): an invalid response is answered like a throwing
  handler, a bare `500` with `connection: close`; pipelined requests after it are dropped.
- HTTP/2 (`HTTP2StreamTask.serve`) and HTTP/3 (`respond`): an invalid response becomes a bare
  `500` on that stream; the connection carries on.
- Each rejection logs an error via `os.Logger` (subsystem `SwiftWebServer`, category `HTTP`),
  on the cold path only (`HTTPFieldValidation.reportRejectedResponse`).
- `HTTP1SerializationError` is now a typealias of `HTTPFieldValidationError` (same cases);
  `HTTP1Serializer.validationError` delegates. `HTTP1ChunkedEncoder.appendLastChunk(trailers:)`
  drops trailers that fail the check (writes the plain last chunk) instead of only asserting.
- `HTTPFields` doc comment, `HTTP1Serializer` doc, `HTTP1` doc and `docs/guide/http1.md`
  updated to describe the release behaviour.

## Gotchas

- A per-field byte-table scan cost about 4 ns per field (42 ns for 10 fields); scanning the
  whole arena at once with 8-byte words brought it to about 2 ns per field. The arena of an owned
  `HTTPFields` holds only names and values, so it is a safe superset to scan; a request-backed
  arena (CRLFs everywhere) simply takes the slow path.
- `HTTPFields.remove` leaves stale bytes in the arena; if they hold a control byte the fast path
  is just skipped, it never causes a false rejection.
- The validation also rejects DEL and C0 controls other than HTAB, which is stricter than the
  CR/LF/NUL minimum of RFC 9113/9114 but matches RFC 9110 §5.5 `field-value`. Leading or trailing
  whitespace in values is not rejected (no protocol here can be split by it).
- `HTTP1Serializer.write` still only asserts: it is the caller's job to validate (the runner and
  `writeValidated` do).
