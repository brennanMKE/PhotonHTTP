## Description

gordon (`Examples/parallax-gordon`) runs laya-swift's `serve` as a separate process behind SwiftWebServer's proxy. That's three LaunchAgents and an extra loopback hop. laya-swift already keeps its decision logic (`Sources/LayaServer/Decisions.swift`, `LayaService.swift`) apart from its own small `HTTPServer.swift`. So a server built from SwiftWebServer could link it and answer `/decision` in-process, which is the clearest demonstration of building a server from parts. Two things block it:
- laya-swift exports only `LayaKit` as a library product.
- No adapter exists that turns its service into an `HTTPHandler`.

## Scope

- **laya-swift side** (its repo and session, with the owner's OK): a library product, for example `LayaHTTP`, that exposes a `HTTPHandler` for `/v1/decisions`, `/predict`, `/health` and `/stats`, depending on SwiftWebServer's `HTTPCore` (version-pinned after #0133). The handler must not block the connection task while the GPU runs. Its own `serve` command can keep its current server or switch to this.
- **SwiftWebServer side:**
  - An example package, for example `Examples/decision-server`, that uses #0131's entry point and #0132's config registration: the shipped config (static files, auth, access log, metrics, proxy) plus an in-process `"decision"` component.
  - Optionally switch gordon's deploy to it, so `/decision` drops from three processes to two.
  - Measure in-process against proxied latency and memory on gordon.

## Acceptance criteria

- The example builds against a tagged SwiftWebServer and a laya-swift library product. `/decision/v1/decisions` answers in-process with the same answers as the proxied setup.
- gordon numbers for both setups are recorded in the example's README.

## Relation

- **Milestone:** composability (assembling servers from parts)
- **Blocked by:** #0131, #0132, #0133, and laya-swift exposing a handler library
