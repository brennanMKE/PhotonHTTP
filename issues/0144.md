# 0144 — There is no graceful restart: config that needs a restart means a gap in service

| | |
|---|---|
| **Status** | open |
| **Module** | SwiftWebServer / HTTPServer / NetworkTransport |
| **Platform** | macOS |
| **First seen** | 2026-11-13 |

## Description

Restart-only config changes (#0143) and binary upgrades need a restart. Today that's SIGTERM (drain) and then launchd starting a new process, which leaves a short gap where connections are refused.

## Scope

- `SwiftWebServer restart` (CLI, from #0143) signals the running server (a dedicated signal such as SIGUSR2) to restart **in process**: read and validate the full config; create new listeners on the same ports with `SO_REUSEPORT` (BSD sockets) or the Network.framework equivalent (check NWListener/QUIC port reuse); new protocols and chain; start accepting on the new listeners; then stop the old listeners and drain their connections up to `drainTimeout` (HTTP/2 and HTTP/3 GOAWAY, as in shutdown). launchd still sees one process.
- If any new listener fails to bind, abort and keep the old listeners: never end up serving nothing. Report the result through the status file; the CLI prints it.
- Where a port moves (the config changed the port), the old port drains and closes and the new one opens.
- Binary upgrades: document `launchctl kickstart -k` with graceful drain (a brief gap) as the way, unless an exec-based handoff fits launchd (investigate; don't build it in this issue).
- `SO_REUSEPORT` must stay loopback/tailnet-safe: binding rules from AGENTS.md apply to tests (loopback, port 0 then reuse that port).

## Acceptance criteria

- A test (loopback) keeps a client sending requests in a loop while a restart changes a restart-only setting: no connection is refused, in-flight requests complete, and new connections see the new settings.
- A restart with an unbindable listener reports failure and leaves the old server running.
- docs/guide/running-on-a-mac.md documents restart and how it fits launchd.
