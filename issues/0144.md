## Description

Restart-only config changes (#0143) and binary upgrades need a restart. Today that's SIGTERM (drain) and then launchd starting a new process, which leaves a short gap where connections are refused.

## Scope

- `SwiftWebServer restart` (CLI, from #0143) signals the running server (a dedicated signal such as SIGUSR2) to restart **in process**: read and validate the full config; create new listeners on the same ports with `SO_REUSEPORT` (BSD sockets) or the Network.framework equivalent (check NWListener/QUIC port reuse); new protocols and chain; start accepting on the new listeners; then stop the old listeners and drain their connections up to `drainTimeout` (HTTP/2 and HTTP/3 GOAWAY, as in shutdown). launchd still sees one process.
- If any new listener fails to bind, abort and keep the old listeners: never end up serving nothing. Report the result through the status file; the CLI prints it.
- Where a port moves (the config changed the port), the old port drains and closes and the new one opens.
- Binary upgrades: document `launchctl kickstart -k` with graceful drain (a brief gap) as the way, unless an exec-based handoff fits launchd (investigate; don't build it in this issue).
- `SO_REUSEPORT` must stay loopback/tailnet-safe: binding rules from AGENTS.md apply to tests (loopback, port 0 then reuse that port).

## Acceptance criteria

- A test (loopback) keeps a client sending requests in a loop while a restart changes a restart-only setting: no connection is refused, in-flight requests complete, and new connections see the new settings.
- A restart with an unbindable listener reports failure and leaves the old server running.
- docs/guide/running-on-a-mac.md documents restart and how it fits launchd.

## Root cause

`Server` owned one fixed set of listeners, one registry and one configuration for its whole
life, and its drain was all-or-nothing (shutdown). The only way to apply restart-only keys was
a new process: SIGTERM, drain, launchd starts the server again, with connections refused in
between. Network.framework listeners cannot share a port at all (`allowLocalEndpointReuse` is
`SO_REUSEADDR` only: a second `NWListener`, TCP or QUIC, on the same port fails with
`EADDRINUSE`, measured), so `SO_REUSEPORT` alone could not cover TLS and QUIC.

## Fix

- **Listener generations** (`Server`, HTTPServer). The listeners, registry and configuration
  plus their connections, counters and drain are a `ListenerGeneration`; `run()` serves the
  first, and `restart(configuration:listeners:protocols:grace:)` (public) binds a new one,
  sends it to the serving task group through a low-rate `AsyncStream` (no unstructured
  tasks), then retires the old one. Retiring for a restart: the listeners close (or pass on),
  the connections go on for `grace` (default 1 s, capped by the drain timeout) so one accepted
  just before the swap gets its first request answered, then see their generation's
  `ShutdownSignal` (HTTP/2/3 GOAWAY, HTTP/1.1 drain) and are cancelled at the new
  `drainTimeout`. A shutdown retires every live generation at once. Each generation has its
  own connection limit. `configuration`, `protocols`, `localAddresses` and
  `listenerStatistics` report the current generation; counts sum over generations.
- **Keeping a port served** (`ServerListener.restartable(address:identity:)`). A new listener
  naming a running listener's bound address (same kind):
  - both `PortSharingListener` (new HTTPCore protocol; `BSDSocketListener` conforms): the old
    one turns `SO_REUSEPORT` on, the new one binds with it, both turn it off again (so any
    other bind still gets `EADDRINUSE`); the kernel sends new connections to the newest
    socket. The old one stays open for half the grace (handshakes that reached it complete),
    then `closeAfterPending()` accepts what is queued and closes; the old generation serves
    those.
  - the running one cannot share (NW TLS, QUIC, NW TCP) and identity and ALPN match: it is
    handed over. Such listeners are wrapped at bind time in a relay (`ListenerRelay.swift`)
    whose own task pulls connections for the current accept loop; `detach()` ends the old
    loop's iteration (an epoch) without closing the listener or cancelling its connections.
    One hand-off per connection, on NW listeners only.
  - otherwise (for example TLS ALPN changed by `http2`): the old one closes first, then the
    new one binds (a gap of milliseconds on that port), after every no-gap bind succeeded.
- **Abort.** Any make or bind failure closes what the restart bound, turns sharing off, and
  throws `ServerRestartError` (listener, address, underlying error, and the running listener
  closed for a replacement, if any); the old generation keeps serving.
- **Executable.** SIGUSR2 calls `ConfigReloader.requestRestart()` (new optional `restart:`
  closure, run on the reloader task in turn with reloads). `Launch.restart` (new
  `Restart.swift`) loads and validates the whole config, protocols, identity (in memory only),
  chain and listeners (`makeListeners` marks each listener `restartable`; a port 0 that was 0
  keeps the bound port), calls `server.restart`, and only then swaps the chain, the identity
  and the Alt-Svc advertisement (moved inside the `ReloadableHandler` chain so a moved UDP port
  is advertised anew), updates the reload baseline, prints `restarted; listening …` and records
  `trigger: restart`, `result: restarted` (new `ServerStatus.Result`) and `restarted` in the
  status file; a failure records `failed`. `SwiftWebServer restart` runs `check`, refuses an
  invalid config, sends SIGUSR2 and waits for the outcome (`--timeout`).
- **Docs.** `docs/guide/running-on-a-mac.md`: "Graceful restart", the `restart` command, the
  status file fields, SIGUSR2, and launchd (`SwiftWebServer restart` for config, `launchctl
  kickstart -k` for a new binary; an exec-based socket hand-off does not fit launchd's one
  job, one pid model and was not built).

## Gotchas

- XNU gives every new connection to the newest `SO_REUSEPORT` socket, and `SO_REUSEPORT` can
  be set on a socket that is already listening: that is what lets the old listener open its
  port only for the swap and close it again. Both sockets need it when the new one binds.
- Closing the old shared socket right after the swap occasionally reset a connect under load
  (`connectionReset` on connect: a handshake still in its queue). Keeping it open for half the
  grace before `closeAfterPending()` fixed it.
- A restart before the first generation's accept loops started saw zero accept loops and shut
  the server down when it aborted: accept loops are counted from the generation's creation.
- HTTP/1.1 closes a connection that is between requests as soon as its drain starts, which
  includes a connection accepted a moment earlier whose first request has not been read yet:
  the old generation's grace exists for that.
- Client loops that open a connection per request leave ephemeral ports in TIME_WAIT for 30 s;
  unpaced, a few runs exhaust them (`EADDRNOTAVAIL`, errno 49). The test client is paced.
- A server started without `http3` that turns it on by a restart listens for HTTP/3 but cannot
  advertise it: its chain type has no Alt-Svc step (kept out for the hot path); stderr warns.
- Follow-ups: a connection-rate `sws-bench` run for the accept path; toggling `http2` replaces
  the HTTPS listener with a gap of milliseconds (Network.framework has no per-handshake ALPN
  selection).
