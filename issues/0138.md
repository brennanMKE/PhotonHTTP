# 0138 — A handler's Connection: close is ignored on HTTP/1.1

| | |
|---|---|
| **Status** | resolved |

| **Platform** | macOS |
| **First seen** | 2026-11-13 |

## Description

Found while writing docs/guide/http1.md. `HTTP1Serializer.writeFields` drops the handler's `connection` field (it owns framing) and writes keep-alive anyway, and `HTTP1Connection` never looks at the response. A handler can't ask for the connection to close after its response (after an auth failure, on overload, or to rebalance clients).

## Acceptance criteria

- A response carrying `connection: close` (a list element, case-insensitive) makes HTTP/1.1 write `connection: close` and close the connection after the response, as RFC 9112 §9.6 describes. The serializer still owns the rest of the framing.
- Pipelined requests already read after it are not answered (they're discarded with the connection).
- On HTTP/2 and HTTP/3 the field is still stripped (connection-specific fields are forbidden) and nothing else changes.
- Tests over in-memory transports; no measurable cost in `sws-bench` keep-alive numbers.

## Root cause

Persistence was decided only from the request (and draining) in `HTTP1Connection`; the runner
never looked at the response's fields, and `HTTP1Serializer.writeFields` drops the handler's
`connection` field because the serializer owns framing. So a handler had no way to say "close
after this response".

## Fix

- `HTTP1ConnectionDriver.write` (HTTP1.swift): for a final (`>= 200`), non-tunnel response, if
  `headers.contains(.connection)` (presence-mask bit test) and the field lists `close`
  (`containsListElement`, case-insensitive, any list position), report the new
  `HTTP1Connection.Event.closeRequested` before `.response(kind)`.
- `HTTP1Connection`: `.closeRequested` in `.handling` sets the exchange's persistence to
  `.close` and returns `.proceed` (pure, single action). The existing path then writes
  `connection: close`, and `.responseWritten` returns `.close(.normal)`, so the connection
  flushes, half-closes and lingers; pipelined requests already buffered are discarded unanswered.
- Other `Connection` tokens (e.g. `keep-alive`) are ignored: a handler cannot override the
  client's or the server's close. `1xx`/`.tunnel` responses are unchanged (`101` keeps its
  `connection: upgrade`).
- HTTP/2 and HTTP/3 unchanged: they already drop `connection` from responses.
- Docs: `HTTP1`, `HTTP1Connection`, `HTTP1Serializer` doc comments and `docs/guide/http1.md`
  (keep-alive section and the "When the connection closes" table).
