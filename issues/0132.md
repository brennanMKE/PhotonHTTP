# 0132 — http-config.json can't configure third-party components

| | |
|---|---|
| **Status** | open |
| **Module** | ConfigFile |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |

## Description

`ConfigFile` knows only the built-in components. A third-party package such as a Laya decision handler can't claim a key like `"decision": { "path": "/decision", "checkpoint": "…", "cacheSize": 10000 }`. That key is warned about as unknown and never reaches the package. So a custom server must keep its own settings somewhere else and can't take part in SIGHUP reload or the config's validation and warnings. `ConfigFile.reservedKeys` and `ReservedValue` exist, but nothing lets a package register for one.

## Scope

- A registration API. A package supplies a top-level key (or `components.<name>` entries), a decoder that turns the JSON value into its settings, and a factory that builds its handler or middleware, plus where it goes in the chain.
- Errors and warnings from registered components report the key path the way built-in keys do.
- Registered components are rebuilt on SIGHUP along with the built-ins, using #0131's entry point.
- Avoid Foundation `Codable` in hot paths. Config parsing isn't a hot path, so the existing JSON reader is fine.

## Acceptance criteria

- A test registers a fake component, loads a config that uses its key, and gets the handler in the chain. A bad value produces a keyed error. A reload picks up a changed value.
- An unknown key is still warned about when no component has claimed it.
- Documented in `docs/guide/running-on-a-mac.md` (the config reference) and in the choosing-components guide.
